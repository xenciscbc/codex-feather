# Handoff file tool

Use the installed skill's `scripts/handoff.py` with Python 3.11+ (standard library only). Resolve the script from this skill's actual installation, not the current project or a guessed user profile. Use `-B` to suppress bytecode files. The launcher also disables bytecode for its modules.

Check an available `python`, `python3` or Windows `py -3` interpreter before invocation. If no compatible interpreter exists, ask whether the user wants help installing Python. Install only after agreement and follow the environment's approval rules. While unavailable, read existing records directly if requested; defer writes instead of bypassing the tool.

## Read

`--project` normally discovers the Git root from the supplied directory. Once the directory is validated, command output reports `root` with the requested directory, selected `path`, and `state` (`git`, `non-git`, `explicit`, or `uncertain`). An uncertain root also includes the failure `reason`; Git reporting success without an absolute top-level path is uncertain too and never falls back to the current directory. Read-only operations retain readable results from that path but return `partial`, `complete: false`, exit 2, with the original operation status in `operation_status`; this is not evidence that the project has no pending work. Mutations fail with `project-root-uncertain` before writing anything.

A `--project` path that is itself a link/junction, or that passes through one above the project, is resolved once to its real path: `root.requested` keeps the supplied spelling and `root.path` reports the resolved root that every operation uses. A Git root is the resolved directory or its nearest ancestor that is the repository's top level. A supplied path that crosses a link below the repository root is `uncertain` ("the path crosses a link below the repository root"); confirm the real directory and use it with `--exact-root`.

Confirm the intended root from the current workspace and user scope, then use `--project <confirmed-root> --exact-root` before the command to use that directory literally (resolved as above). This bypasses discovery only and does not change Git trust. It also supports deliberately selected non-Git roots when Git is unavailable. If the root cannot be established from available evidence, ask which project to use rather than creating another handoff under a guessed directory.

```text
python -B <skill>/scripts/handoff.py --project <project> list
python -B <skill>/scripts/handoff.py --project <project> read --work <work>.md
```

Output is UTF-8 JSON for every invocation except `--help`, which prints plain usage text with exit 0. Command-line usage errors return `code: usage` and a missing selected file `code: not-found`, both `status: error`, exit 2; a missing file outside the selected project is `io`. Invalid stdin JSON, including a duplicate key, is `code: input`. Exit 0 means the operation was handled; distinguish `status: missing` from an existing empty collection. Exit 2 means `partial` or `error`: retain readable items, report issues and scope, and never infer no pending work or select the sole unfinished work from incomplete results. `version` is a content digest for subsequent update checking, not proof of work correctness. `content` preserves the full source text; list items are summaries only. `record_status: 完成待歸檔` means the completed work file still exists, not proof that history has or has not already been saved.

Reads do not write records or Git rules. Inspect the full selected work and relevant current project sources before resuming. Inside the project, the tool rejects symbolic links, junctions and other name-surrogate reparse points, reparse points whose tag cannot be identified, and hard links (`.feather`, records, history, archive and snapshot sources) rather than following aliases. Reparse points that are not aliases, such as cloud-file placeholders and deduplicated files, are used as ordinary files and directories; when `lstat` follows such a point, its tag is taken from the parent directory listing. Every operation also confirms that the resolved root still resolves to itself; a root replaced after resolution fails with `unsafe-path` ("Project root changed after it was resolved") before writing. On a volume that cannot resolve real paths, links anywhere in the supplied path are refused instead. Different work files may have the same title; use the returned filename to distinguish them.

`snapshot_state` is `absent`, `available` or `invalid`; list/read do not hash sources. When capturing a baseline or resuming a record that has one, follow [Source baselines and resume comparison](snapshots.md) for the read-only `snapshot` and `compare` commands and the optional create/update `snapshot` payload. Ordinary read/list requests do not invoke comparison.

## Create

Use `create --work <work>.md` with one UTF-8 JSON object on stdin. The work name is a direct basename with a nonempty name before `.md`, other than `history.md`; a file named just `.md` is not a work and is never listed. Supply `title`, a `fields` object, and optional `details` text. Field keys are `goal`, `progress`, `next`, `notes`, `environment`, `verification`, `decision`, `updated`, `status`; required goal/progress/next must be nonempty. A supplied optional field must not be blank either: omit it instead of sending empty or whitespace-only text (create and update return `input`). The tool supplies a zoned update time and `進行中` status when omitted. Status values are `進行中`, `受阻`, `完成`. Values are single-line text; long evidence belongs in `details`, rendered under `## 詳細紀錄` with LF line endings.

The Agent writes `progress` as one or two concise sentences with concrete findings and the main pending work. Preserve full evidence and constraints in the other fields/details. The tool validates structure, not truthfulness or semantic completeness. Use structured stdin or a UTF-8 input file; never concatenate user text into shell code.

`tracking` may be `default` or `track`; it respects existing tracking and effective ignore rules. `track` removes only this tool's exact `/.feather/handoffs/` rule and records the choice as the comment line `# cc-feather: track /.feather/handoffs/` in the project `.gitignore`, in one write that keeps its line endings. Later default saves see that marker and report `existing-rule` without adding the rule again; delete the marker line to restore default behavior. The marker is a Git comment and never unignores anything: broader ignore rules still win and are reported as `tracking-blocked`. The tool does not stage or commit. A tracking failure after create/update returns `status: partial`, `code: tracking-failed`, `work_path`, `saved_version`, the observed `state` and a `recovery` text; when readable, `version` identifies the current work. Inspect the surviving work and Git rules. After resolving the tracking issue, retry update with the current version. A completed work (`狀態：完成`) is not archived after a tracking failure and refuses normal updates, so run `archive` with `{ "version": "<current version>", "tracking": "<same choice>" }` instead; it archives the work and then applies tracking. Never repeat create over the saved file.

The tool is not a lock or a cross-session transaction system. Keep one writer for a work item and serialize all shared-history operations externally. A content version check does not close the gap between checking and writing. When writing a newly created file fails, the tool removes only the partial file it created (matched by file identity) and reports the original error; a replacement by another writer between that identity check and the removal is not excluded. When replacing an existing file fails, the tool removes its temporary file and reports the original error; a read-only target is reported as `read-only` and left unchanged.

## Update and completion

Use `update --work <work>.md` with `{ "version": "<read version>", "fields": { "progress": "...", "next": "..." } }`. Optional `title` and `details` replace only those requested values; other fields and manual sections remain. Read the complete work first. Preserve evidence when replacing details. An empty/multiline legacy field or duplicate field needs an explicitly reviewed full `replacement` string plus `version`, without partial fields. This is for authorized, semantically clear normalization; ask about ambiguous content before submitting it. Read-only requests never normalize files.

The managed details section ends at the next heading of the same or higher level, preserving siblings such as `## 詳細紀錄補充`. Duplicate exact `## 詳細紀錄` headings require a reviewed replacement instead of an ambiguous partial edit. Updating the managed heading preserves its existing LF/CRLF line ending.

A details update must keep the level-1/2 headings that follow the managed section unchanged and outside code fences. Details that would hide or change them (for example an unclosed code fence) are refused with `details-format` and nothing is written; close the fence or use `###` headings. The update result lists those sibling headings in `preserved_sections`. A level-1/2 heading inside details (outside a fence) starts a separate section: the save succeeds, the create/update result carries a `warnings` entry for it, and later details updates replace only the text before it.

Existing details that already hide level-1/2 headings inside a code fence also refuse a details update with `details-format`, when the fence is still open at the end of the details or also holds a fenced block with an info string (such as a swallowed `## 檔案基準` JSON block): replacing the details would drop those sections. Nothing is written; repair the work with a reviewed `replacement`. Headings inside a closed, self-contained fenced example are replaced with the details as usual, except that such an example followed by a fence left open to the end of the details is also refused, even when that open fence hides nothing. The text alone cannot tell this from an unclosed opener that swallowed a later section holding a bare code block, whose opening fence line closes the opener and whose closing fence line is left open; allowing it would silently drop that section. To proceed, close the trailing fence or turn the example's headings into `###` headings by hand, or repair the work with a reviewed `replacement`. Not detected: an unclosed opener in details followed by a manual section that ends with exactly one bare fence line.

Every normal create/update with `status: 完成` saves the final work and automatically archives it. Its zoned `updated` value is the completion identity; do not reset it on retry. If archival fails after the completed work was saved (for example `history.md` has unrecognized content), the result is `status: partial`, `code: archive-failed` with the underlying `cause_code`, `work_path`, `saved_version` and `recovery: retry-archive`; resolve the cause, then retry with `archive` instead of repeating the save. If another session is known to be writing shared history, use `defer_history: true` to retain the completed work for a coordinated retry. Use `archive --work <work>.md` with `{ "version": "<current read version>" }` to retry an already completed work, adding `"tracking": "track"` when that was the save's choice (default `default`). The tool verifies saved history before checking and removing the identical work source. After a successful archival, `archive` applies the tracking choice like a save and reports it in `tracking`; if that fails, the result is `status: partial`, `code: tracking-failed` with `archived: true`: history is saved and the work removed, so do not retry archive; resolve the Git rules (a later create or update applies tracking again). Preserve and report conflicts, pending work paths and any surviving history; do not retry create or modify completion identity to bypass a failure.

Create and update refuse a `status: 完成` save whose body would not archive exactly (for example a line that looks like a history entry marker `## <title> · 完成：<time>`); nothing is written, so reword the body first. A completed work already stuck that way (archive reports `format` and names the offending line) has one permitted edit: `update` with `{ "version": "<read version>", "replacement": "<reviewed full text>" }` (optionally `tracking`/`defer_history`) that keeps the same title, `更新` and `狀態：完成`, passes the same archive check, and whose identity is not already in history; it is then archived as usual. Any other update of a completed work returns `completed`.

## History and explicit selections

Use `history` with optional `--work <title>`, `--from-date YYYY-MM-DD`, `--to-date YYYY-MM-DD`, `--keyword <text>`, `--timezone <zone>` and `--include-sealed`. Pass the user's timezone explicitly; when unavailable, state that the tool defaults to UTC. Date limits are inclusive. UTC and fixed offsets such as `+08:00` work without timezone packages; IANA zones require host timezone data. Unsupported zones produce an error rather than an assumed conversion.

Results include full entries, `id`, `source`, `document_version`, and boundary problems. Querying is not authorization to mutate. Resolve user selections to exact returned identities and sources; ask when same-name identities or boundaries are ambiguous. Incomplete queries cannot prove an exhaustive selection.

For explicitly authorized clearing, use `clear` with `{ "source": "history.md", "version": "<document_version>", "ids": ["<id>"] }`. Omitted source means shared history; sealed files require the explicit `archive/<batch>.md` source. To clear all recognized shared entries, enumerate their IDs from a complete query. Unknown content is preserved for clarification. Each source is a separate coordinated operation. Stale or missing selections are refused: reread and reconcile the original selection instead of switching to another same-name entry. Work files are never a clear source.

For explicitly authorized sealing, use `seal` with `{ "version": "<shared document_version>", "ids": ["<id>"], "destination": "<batch>.md" }`. The tool checks direct work files for unfinished archival before both first attempts and retries, saves and verifies the complete destination, then removes only the same source entries. An existing identical destination is reused; different contents are preserved as a conflict.

Before writing, `clear` and `seal` read every direct work file. A completed work holding a selected identity returns `pending-archive`, or `conflict` when its body differs from that entry; this check comes first. `pending-unknown` means a work may be an unfinished archival: it is unreadable or undecodable; it is malformed with no title on the first line or without exactly one status line reading `進行中` or `受阻`; or it is otherwise well-formed but holds more than one status line or a merge-conflict marker line. A status line is any line that starts with `狀態` and a full-width or ASCII colon after optional spaces or tabs, inside code fences and indented lines too. A marker line starts with `<<<<<<<`, `>>>>>>>` or `|||||||` followed by a space or the line end; `=======` is not checked because it also underlines setext headings. Nothing is written. Resolve a merge conflict first. Reword a status line that is only quoted text so it no longer starts with `狀態` and a colon (for example inline code or a `- ` or `> ` prefix); a completed work can instead be archived, or given a reviewed `replacement` that keeps its title, `更新` and `狀態：完成`. Other malformed works do not block the operation and are listed in the result's `warnings`.

On a partial seal, retain the reported destination and original IDs. Query the current shared history version and retry the same selection/destination, adding `destination_version` from the partial result. This allows an already moved source entry to remain absent without substituting another record. If no destination version was obtained, inspect the destination through an explicitly inclusive history query before retrying. Every retry checks pending completed sources again. An empty history still has a document version in the query's `documents` list. Preserve both copies and report the actual paths if reconciliation is uncertain.
