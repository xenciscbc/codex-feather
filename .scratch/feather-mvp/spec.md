# codex-feather：輕量任務分工第一版

Status: ready-for-agent

## Problem Statement

使用者希望在自己的 Codex 日常工作中，依任務性質分配適合的模型，保留主 Agent 對需求、整合與最終結果的責任。

先前的分工容易把「讀原始碼或文件」一律視為查找，讓需要邏輯推導的分析落到能力定位不符的 scout。另一方面，完整的多角色審查流程又超出使用者需求，增加設定與協調負擔。

使用者需要清楚的角色界線、可核對的模型使用情況，以及簡單扼要的成果回報。選角適當且成果可靠即有價值，不以省時或省用量作為第一版的必要成功条件。

## Solution

交付一套輕量分工規則、四個固定角色模板與隔離測試。主 Agent 判斷直接處理或委派，依工作性質選角，收回並整合成果。

查找事實交給 scout；原始碼或邏輯性文件的分析交給唯讀 analyst；完整規格的重複修改交給 mech-executor；需要局部工程判斷的實作交給 executor。小任務與難以拆開的整體推理由主 Agent 直接完成。需要其他獨立職責時，沿用原生通用子 Agent 能力，不預先擴張固定角色。

本版先供使用者本人試用。成果先說結論，只附必要證據、未確認事項及待決問題。安裝器與舊環境遷移留待後續。

## User Stories

1. As a 使用者, I want 在自己的日常任務中試用分工, so that 我能判斷它是否實際有用。
2. As a 使用者, I want 小任務由主 Agent 直接完成, so that 簡單工作不增加交接成本。
3. As a 主 Agent, I want 依推理需求而非是否唯讀來選角, so that 分析工作不會被誤歸為查找。
4. As a 主 Agent, I want 讓 scout 找位置、擷取內容並整理引用事實, so that 我能快速取得可靠素材。
5. As a 主 Agent, I want 讓 analyst 分析原始碼的邏輯與影響, so that 分析有獨立且明確的責任歸屬。
6. As a 主 Agent, I want 讓 analyst 分析文件的論證與矛盾, so that 邏輯性閱讀不被當成單純擷取內容。
7. As a 使用者, I want analyst 保持唯讀, so that 分析發現不會自行變成修改。
8. As a 主 Agent, I want 收到 analyst 的證據、推論與建議, so that 我能決定是否修改以及後續如何分工。
9. As a 主 Agent, I want 將規格完整的重複修改交給 mech-executor, so that 明確的機械工作有適合的執行者。
10. As a 主 Agent, I want 將需要局部設計的實作交給 executor, so that 工程判斷不會被誤當成機械修改。
11. As a 主 Agent, I want 保留持續整合全局資訊的推理, so that 同一問題不因強制拆分而失去上下文。
12. As a 主 Agent, I want 能從複雜工作切出獨立分析問題, so that 有明確產出的部分仍可委派給 analyst。
13. As a 使用者, I want 固定角色有明確的模型與 reasoning 設定, so that 選角意圖能對照設定及實際執行。
14. As a 使用者, I want 保留目前選擇的主模型與 reasoning, so that 分工工具不改變我的主工作環境偏好。
15. As a 主 Agent, I want 用通用子 Agent 承接不屬於四種固定角色的獨立工作, so that 不必為每種專業新增固定角色。
16. As a 子 Agent, I want 收到目標、背景、範圍、限制、產出與完成條件, so that 我能完成有邊界的子任務。
17. As a 主 Agent, I want 只並行沒有依賴或資源衝突的工作, so that 委派不造成互相覆寫或使用未完成成果。
18. As a 子 Agent, I want 明確的修改範圍與檔案所有權, so that 我和其他執行者能避免寫入衝突。
19. As a 主 Agent, I want 子任務卡住時繼續無依賴的工作, so that 單一阻礙不拖住整個任務。
20. As a 主 Agent, I want 發現能力或規格不匹配時收回並重新分工, so that 不會反覆重試同一個錯誤派工。
21. As a 使用者, I want 主 Agent 整合子任務的缺漏與矛盾, so that 最終成果有人負責而非只是轉貼子 Agent 回覆。
22. As a 使用者, I want 簡短看到分工原因、角色與結果, so that 我能理解分工是否適當而不必閱讀長篇紀錄。
23. As a 使用者, I want 區分預期模型、設定值與執行證據, so that 我能辨識派錯模型或尚未確認的情況。
24. As a 使用者, I want 先在隔離環境驗證規則與模型綁定, so that 試驗不影響真實 Codex 設定。
25. As a 使用者, I want 只記錄有可信來源的耗時與用量, so that 效率判斷建立在實測而非推測。

## Implementation Decisions

- **交付邊界**：第一版交付分工指令、四個固定角色模板、隔離測試及必要的使用與驗證說明。目前專案只有設定與設計文件，沒有既有產品實作可沿用。
- **規則與角色分離**：分工時機、選角、依賴、brief、整合及回報規則放在生效的 Agent 指令來源；固定模型、reasoning 與基本職責放在原生角色 TOML 模板。指令中的模型名稱不能取代原生模型綁定。
- **固定角色的預期配置**：scout 使用 gpt-5.6-luna／low；mech-executor 使用 gpt-5.6-luna／medium；executor 與 analyst 使用 gpt-5.6-sol／medium。這是待實測的配置，不宣稱是最佳配置。
- **查找與分析界線**：scout 提供位置、擷取內容與有引用事實。需要理解因果、推導邏輯、辨識矛盾或評估影響的原始碼與文件工作屬於 analyst；唯讀不是選擇 scout 的充分條件。
- **分析權限**：analyst 保持唯讀，只提供證據、推論與建議；主 Agent 決定後續修改與執行者。不能把分析發現當成自行修改的授權。
- **主 Agent 保有選擇權**：能切出明確問題與產出時可委派 analyst；持續整合全局資訊或反覆推導同一問題時由主 Agent 直接處理。分析不必經過 analyst，小任務也不強制委派。
- **通用子 Agent**：不屬於固定角色而值得獨立處理的工作，可使用通用子 Agent，預期繼承主 Agent 的模型與 reasoning。實際原生支援方式與繼承行為必須查證；若不支援，不靜默換成較輕模型或宣稱已繼承。
- **使用者偏好**：不覆蓋主模型、reasoning 或並行數，不採用 Spark。Astra／medium 是先前討論的參考配置，不是強制主模型。
- **派工契約**：每次派工交代目標、必要背景、範圍、限制、產出及完成條件。寫入任務需指定所有權範圍，主 Agent 與其他子 Agent 避免同時修改該範圍。
- **依賴與失敗處理**：只並行沒有依賴路徑、寫入衝突或共享可變資源衝突的任務。卡點只阻擋依賴它的工作；規格或能力不匹配時由主 Agent 收回、澄清或重新分工，不強制重試相同派工。
- **整合責任**：主 Agent 處理成果缺漏、矛盾與最終判斷。規劃、授權、審查、資安與驗收方法服從環境、使用者或其他技能的要求，本工具不新增固定關卡。
- **回報契約**：先回報結果；有委派時簡述子任務、選角原因、角色、模型／reasoning 的確認狀態與結果。必要時補充返工、接手或阻礙；不預設長篇分析或大型表格。沒有委派時簡述由主 Agent 直接完成。
- **證據分層**：分別表示預期角色與模型、模板或請求中的設定、原生執行紀錄中的實際值。未取得可信執行資料時標記未確認，不能用自述或設定值證明實際模型。
- **先查證再配置**：實作首先核對當前 Codex 原生角色 schema、生效指令優先順序、通用子 Agent 繼承與可取得的執行紀錄欄位。將查證結果用於最小可用模板及隔離驗證；不在本規格中假定未查證的欄位或 API。

## Testing Decisions

- **主要測試入口**：在隔離 Codex 環境載入候選規則與角色模板，從使用者提出任務到主 Agent 回報成果，測試完整的外部行為。沿用訪談中已確認的五種情境，不另建立多套內部測試介面。
- **測試對象**：分工規則、角色選擇與模型綁定、唯讀及修改範圍、主 Agent 整合與簡短回報。專案目前沒有既有產品測試或類似測試框架。
- **好測試的標準**：使用具體素材與可檢查的預期結果，驗證成果及副作用；不以提示詞包含特定句子或主 Agent 自述已遵守規則作為通過證據。

| 情境 | 可觀察的完成條件 |
| --- | --- |
| 查找設定或符號 | scout 找到正確位置並提供可核對引用，保持唯讀。 |
| 分析原始碼或邏輯文件 | analyst 提供有證據的推論，辨识測試素材中的邏輯或矛盾，保持唯讀，將修改決定交回主 Agent。需涵蓋原始碼與文件兩類素材。 |
| 完整規格的批次修改 | mech-executor 完成指定修改，結果符合事先規格，修改維持在指派範圍內。 |
| 需要局部工程判斷的修改 | executor 完成符合需求的實作，由成果行為及適當檢查驗證正確性，修改維持在指派範圍內。 |
| 小任務或不可拆開的整體推理 | 主 Agent 直接完成，無不必要委派，結果符合任務要求。 |

- **邊界情境**：沿用同一入口，核對唯讀分析不被派給 scout；子任務阻塞時無依賴工作能繼續；衝突或依賴工作不被不當並行；主 Agent 處理互相矛盾的成果。使用可控制的測試素材，不要求建立排程引擎。
- **原生相容性**：靜態檢查模板格式與預期綁定，並以原生執行證據核對四種角色的實際模型與 reasoning，以及通用子 Agent 的繼承。靜態正確不等於執行確認；證據缺失時記錄未確認，不能宣稱完整綁定／繼承驗證通過。
- **隔離與用量**：測試不修改真實 Codex home 或既有角色配置。會使用模型用量的真實 smoke test 必須明確啟用，不隱藏在一般靜態檢查中。
- **成功門檻**：選角適當、成果可靠、權限範圍正確、回報扼要且證據狀態誠實。耗時與用量只記錄可取得的可信資料，不設節省門檻，不把缺失資料當成零。完整對照效能評測留待後續。

## Out of Scope

- 安裝器、更新、移除與舊 Pilotfish 遷移。
- 寫入真實 Codex home、替換既有角色或移除既有 hook。
- Plugin、marketplace、額外 Skill 包裝與對外發布。
- 強制 Plan、固定審查鏈、新增核准或資安關卡、阻擋 hook。
- Spark 及擴張成大量固定專業角色。
- 自建 daemon、dashboard、持久化工作流引擎或完整紀錄核對工具。
- 保證節省時間或用量，以及宣稱模型配置已最佳化。
- 面向陌生使用者的完整安裝體驗與廣泛跨平台相容性承諾。

## Further Notes

- 本規格依 2026-09-07 已定案訪談整理。四角色設計取代較早草稿的三角色配置；analyst 是本輪明確新增的角色。
- 生效的環境規則與本產品要交付的分工規則是不同層次。開發期間存在的 Pilotfish 指令仍按其優先順序適用，不能因此將 Pilotfish 的完整流程納入產品。
- ready-for-agent 表示規格可進入後續任務拆分與實作流程，不表示已完成產品、通過原生驗證，或已授權安裝、遷移及發布。
- 下一步可依本規格拆分工作；原生能力查證是相關模板實作與執行驗證的前置依賴。若結果不符合已定案的模型或角色契約，明確回報差異，不能靜默縮減要求。
